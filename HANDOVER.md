### Announcer (session 2, for team review)

The fight announcer now plays **recorded clips through a Web Audio effect
chain** instead of browser speech synthesis. This replaces the flat robot
voice, which was a deliberate joke in the original design; Rhaveen found it
robotic and asked for an arcade fighting-game announcer, so this change is
for the team to accept or reject.

- **Voices (chosen by ear by Rhaveen on 2026-11-15 on a dev-only audition
  page, since removed):** every line is Kenney's "Voiceover Pack: Fighter"
  (CC0) with the `deep` treatment, except **"Fight", which is Alba
  MacKenna's own-FX recording (CC-BY 4.0, credit required, see CREDITS.md)
  with the `demonPlus` treatment**. Rhaveen chose a second voice for "Fight"
  knowingly, for more energy.
- **Where to change it:** `voice` in `src/manifest.ts`. `clips` maps each
  line to a file; `preset` is the treatment for all lines; `linePresets`
  overrides it per line; `presets` holds the treatment numbers (pitch via
  `rate`, `drive`, `lowBoost`, `highCut`, `reverb`, `echo`, `gain`, ...).
  The effect chain is `src/core/voicefx.ts`; which clip a line uses is the
  pure `planAnnounce` in `src/core/announcer.ts`.
- **Still speech synthesis:** the fallback when a clip is missing or fails
  to load, and "Upgrade!" in the shop (no recording exists).
- **Fish names are no longer spoken** (`voice.speakFishName: false`); no
  recording can say them and the name is on screen. Set it to `true` to
  have the synthesised voice say the name after the recorded "Round N".
  Rhaveen has not given a clear answer on this, so treat it as open.
- **Rounds:** recorded "Round one" to "Round five"; from round 6 the generic
  clip says "Ready".
- **Win lines:** there is no "K.O." recording in this pack, so a win says
  "You win", a perfect win "Flawless victory", a time-out "Time", a loss
  "You lose".
- Rejected along the way: packs under CC-BY-SA (VoiceBosch), which would
  force share-alike on the game's assets; Aimee Smith's and Kenney's other
  pack (auditioned, not chosen); Wozniak and qubodup (too few lines).

### Deployment and pull request previews

- **Every pull request is tested, built and published** by
  `.github/workflows/preview.yml` to the `gh-pages` branch under
  `pr-preview/pr-<number>/`, and a bot comments the play link on the PR
  (`https://yurtemre7.github.io/samurai-hook/pr-preview/pr-<number>/`). The
  folder is removed when the PR closes. This also gives every PR a test run.
  Pull requests from forks are skipped (their token is read-only).
- **GitHub Pages serves the `gh-pages` branch** (Settings, Pages, Source:
  "Deploy from a branch", `gh-pages`, `/ (root)`; switched on 2026-11-15,
  issue #21). Do not change it back to "GitHub Actions": the preview links
  and the live site both depend on it.
- **`main` is published** by `.github/workflows/pages.yml` to the root of
  `gh-pages` on every push, after the tests pass. The `pr-preview/` folder is
  left alone.
- Two third-party actions are used, pinned to major versions:
  `rossjrw/pr-preview-action@v1` and `JamesIves/github-pages-deploy-action@v4`.
- **itch.io**: `.github/workflows/itch.yml` runs on every push to `main` (and
  manually via "Run workflow"). It runs `npm ci`, `npm test`, `npm run build`
  and pushes `dist/` with itch's official `butler` CLI (downloaded from
  `broth.itch.zone`) to `yurtemre7/samurai-hook:html5`, with the user version
  `<package.json version>+<short SHA>`. Target and channel are in the
  workflow's top-level `env:`.
  - Until the `BUTLER_API_KEY` repository secret exists the workflow is
    skipped with a `::notice::` (it does not fail, so `main` stays green).
  - One-time setup, by the itch.io account owner:
    1. On itch.io go to Settings, API keys
       (https://itch.io/user/settings/api-keys) and generate a new API key.
    2. In the GitHub repo go to Settings, Secrets and variables, Actions,
       New repository secret. Name it `BUTLER_API_KEY` and paste the key.
    3. On the itch.io game's Edit page make sure "Kind of project" is HTML.
       After the first automated upload, tick "This file will be played in
       the browser" for the `html5` channel upload, and remove any old
       manually uploaded zip so players get the automated build.
    4. Re-run the workflow from the Actions tab ("Run workflow").

## Decisions

- Fight controls: 4-button duel (move, quick slash, heavy slash, defend).
- Art: CC0 pixel art; code-drawn placeholders where no licence is confirmed.
- Roster: 8 to 10 fish; the plan has 9.
- Shop: 3 endless tracks only (damage, max depth, gold bonus).
- Audio: CC0 sound files, credited.
- Humour: anime fight announcer.
- PRs: the orchestrator merges its own PRs after its checks.
- Gamepad: tested with a simulated gamepad, then confirmed by a human.

Orchestrator's calls (small and reversible):

- Vite + TypeScript + Canvas 2D, no engine, because the fight logic stays
  pure and testable and there is no framework for the team to learn.
- Progress is saved in localStorage.
- Below 170 m the roster repeats in tougher, richer tiers.
- "Equipment" is the name of each damage level, not separate items.
- Losing a fight costs only the fish.
- The design doc lives at docs/DESIGN.md.
- The plan was approved on 2026-11-14, with the spoken announcer (browser
  speech synthesis, switch in `manifest.ts` under `voice`).
- `src/game/state.ts` was written by the orchestrator in the scaffold
  instead of by a subagent, so that every other module could run against
  real gold, upgrades and fish data from the start.

  Agents report in their PR description and the orchestrator updates this
  file when it merges. (The fight agent may extend fight-related parts of

## Known issues and open questions

- The first commit (plan and scaffold) went straight to `main` because an
  empty repo gives pull requests no base. Everything after it goes through
  PRs.
- The round counter and save persist in localStorage; use
  `game.state.reset()` to start over.
- `npm test` prints a large balance table; that is intended.
- Open question for the team: is the stand-in squid acceptable, or should
  it stay a placeholder until a better sprite is found?
- **W A S D in the fight (reported by Rhaveen, Chrome on a Mac), fixed:** A
  and D did not move the samurai while the arrow keys and J K L E worked.
  The fix does two things, and Rhaveen confirmed on 2026-11-15 that held A
  and D now walk. Which of the two was the cause on that machine was never
  isolated: (1) the game now claims every bound key with `preventDefault`
  (no modifiers held), as it already did for the arrows, so macOS
  press-and-hold cannot interrupt a held letter; (2) W A S D J K L E are
  also bound by the printed letter (`KeyboardEvent.key`), not only by key
  position, for non-QWERTY layouts. Also: an autorepeat key-down no longer
  latches a fresh tap, and the fight and shop hints show `A D` only, since
  up and down do nothing there.
- **Key debugger:** add `?debug=keys` to the URL to see what the browser
  reports for each key event and which action it mapped to. Use it first
  for any future "key does nothing" report.
- Pull requests are tested and built by the PR preview workflow (see
  "Deployment and pull request previews"); the bot's comment has the play
  link.
- Scripted browser checks cannot watch fights in motion when the browser
  pane is hidden, because a hidden page pauses its game loop. PR #20 was
  checked by tests, the balance table and still screenshots only.
